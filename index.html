How to read these

  • S is the start pose. Numbered badges are the end point of each leg, in driving order.
  • Small dots with no number are Bézier control points — the robot never drives through them, they only bend the curve.
  • The last leg (and badge) is always PARK.
  • Coordinates are Pedro field inches, origin at the field corner, 0–144 on both axes. Headings are degrees, 0° = +X, counter-clockwise positive.

One route, many OpModes

The drive paths are identical across all four code sets — the top-level auto/ package and the singleshooter/, singleturret/ and doubleturret/ forks all contain the same coordinates. That is why each route is drawn once here. What differs is what happens at the points:

Code setOpMode prefixBehaviour at a pointChanges the driven path?
auto/(none)No shooter at all — drives the route, holds 2 s per pointNo
singleshooter/1SFixed shooter, no turret — drives a short approach toward the hive, then shootsYes — see below
singleturret/1TTurret aims itself — shoots in placeNo
doubleturret/2TTwo turrets aim themselves — shoots in placeNo

The 1S difference is real but not drawn here. In singleshooter/, RobotConfig passes null for the turret, so Scorer.hasTurrets() is false and every shooting point inserts an extra approachPath() — a short straight drive of up to APPROACH_DISTANCE = 8" toward the hive, ending facing it, never closer than MIN_HIVE_DISTANCE = 30". 1T and 2T skip it entirely.

Those approach segments are not drawn on these diagrams, because they aim at FieldPositions.Blue.GOAL, which is still a TODO(field) placeholder (14, 130). Drawing them now would show a line to a made-up target. Once the real goal pose is measured, they can be added.

Accuracy

  • Every coordinate was read straight out of the Java sources, then a script re-extracted every point from the drawn SVG and compared the two sets — all seven routes matched exactly, including control points and the park spot.
  • The curves are the visualizer's own Bézier output for the control points in the code, so the bend you see is the bend Pedro will follow.
  • Path lengths on each page are computed from that drawn geometry. No drive times are shown: Pedro is not tuned yet (pedro/Constants.java still holds placeholders), so any time estimate would be fiction.
